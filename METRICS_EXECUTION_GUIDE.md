# Tally metrics execution guide

**Original baseline date:** 20 November 2026. Baseline metrics below were collected using Vitest 3.2.7, Lighthouse 12.8.2, Chromium headless, axe-core via `@axe-core/playwright` 4.10.2, and pnpm 9.15.0 where invoked through Corepack. A later improvement snapshot, using Vitest 4.1.12 and the same Lighthouse/axe versions, is recorded in section 8.

Sections 1–7 preserve the original baseline and repeat instructions. They are historical after the improvement pass; do not mistake those original findings for current results.

## 2. Accessibility audit

The axe/Playwright run scanned seven public/UI routes. All seven test cases failed the zero-violation assertion. Across those routes it found **9 route/rule violations affecting 20 element instances**; every reported issue had `serious` impact.

| Route              | Violated rules                           | Affected elements |
| ------------------ | ---------------------------------------- | ----------------: |
| `/login`           | `color-contrast`                         |                 2 |
| `/register`        | `aria-prohibited-attr`, `color-contrast` |                 6 |
| `/forgot-password` | `color-contrast`                         |                 2 |
| `/reset-password`  | `aria-prohibited-attr`, `color-contrast` |                 4 |
| `/verify-email`    | `color-contrast`                         |                 2 |
| `/offline`         | `color-contrast`                         |                 1 |
| `/ui-preview`      | `color-contrast`                         |                 3 |

That is 9 route/rule pairs and 20 affected nodes; it does not mean 9 distinct underlying defects, since a shared component or color can recur across routes. Scans covered WCAG 2.0 A/AA, WCAG 2.1 A/AA, WCAG 2.2 AA, and axe best-practice tags. The scan ran against the local development server; authenticated/protected routes were not included.

The baseline command was `cd tally_web && pnpm test:a11y`. The historical baseline found the issues listed above. Current result: all seven routes pass after contrast, ARIA, and checkbox-name fixes; see section 8.

## 3. Lighthouse

Lighthouse scanned production `/login` at `http://127.0.0.1:3000/login`. It used Lighthouse 12.8.2 and Chromium headless (reported user agent: HeadlessChrome 156). There were three desktop runs and three mobile runs. Scores below are medians; the range shows run-to-run spread.

| Emulation |    Performance | Accessibility | Best Practices | SEO |      FCP |      LCP | CLS |    TBT |
| --------- | -------------: | ------------: | -------------: | --: | -------: | -------: | --: | -----: |
| Desktop   | **97** (75–97) |            96 |             96 |  60 |   290 ms | 1,252 ms |   0 |  26 ms |
| Mobile    | **74** (71–74) |            96 |             96 |  60 | 1,057 ms | 4,862 ms |   0 | 365 ms |

The first desktop run was an outlier: its LCP was 25.2 seconds, while the two repeat runs were 1.25 and 1.23 seconds. The reported median reduces the effect of that single reading, but the spread is retained because the cause has not been established. These measurements are for local production build/runtime, not a public deployment or real-user telemetry.

HTML/JSON reports are in [`artifacts/lighthouse/`](./artifacts/lighthouse/), including the three-run JSON readings for each emulation. Lighthouse has no lab INP value here; INP needs interaction/field measurement.

## 4. Production build and bundle output

The production command `next build --webpack` succeeded in the elevated environment. It emitted **15 route entries**: 14 application page routes plus `/_not-found`; the `[id]` application detail route was dynamic, and the other 13 page routes were static. The build also reports the Proxy middleware.

From that build:

- `.next/static/chunks`: **3.1 MB** on disk
- JavaScript chunks: **45 files**, **2,940,231 bytes raw**, **933,246 bytes when each file is gzip-compressed**
- Next build output: **15 route entries** (13 static app pages, one dynamic `/applications/[id]` page, plus `/_not-found`).

The raw/gzip totals aggregate every client JS chunk, not a route-specific first-load transfer size. The two numbers should only be compared across builds with the same Next version, build mode, and measurement command.

## 6. Repeat commands

```sh
cd tally_web
pnpm test:coverage
pnpm test:a11y
pnpm build
```

Run the production app with `pnpm start`, then run Lighthouse with the same route and settings. The Playwright and Lighthouse browser runs require the installed Chromium browser.

For repeatable Lighthouse output, point the production build at the local test API stub (not the staging API), start the stub in a separate terminal, then serve the production build and run Lighthouse:

```sh
cd tally_web
pnpm metrics:api-stub
```

```sh
cd tally_web
NEXT_PUBLIC_API_URL=http://127.0.0.1:59999/api/v1 pnpm build
pnpm start
```

```sh
cd tally_web
PLAYWRIGHT_CACHE="$(node -e 'process.stdout.write(require("node:os").homedir())')/.cache/ms-playwright"
export CHROME_PATH="$(find "$PLAYWRIGHT_CACHE" -path '*/chrome-linux64/chrome' -type f -print -quit)"
pnpm exec lighthouse http://127.0.0.1:3000/login --preset=desktop --output=html,json --output-path=./artifacts/lighthouse/login-desktop --chrome-flags="--headless"
pnpm exec lighthouse http://127.0.0.1:3000/login --form-factor=mobile --output=html,json --output-path=./artifacts/lighthouse/login-mobile --chrome-flags="--headless"
```

For aggregate build chunks, collect both raw and compressed bytes after the successful build:

```sh
du -sh .next/static/chunks
find .next/static/chunks -type f -name '*.js' -exec wc -c {} + | tail -1
find .next/static/chunks -type f -name '*.js' -exec gzip -c {} + | wc -c
```

```sh
cd tally_api
pnpm test:coverage
pnpm audit --prod --json
pnpm audit --json
```

```sh
cd tally_web
pnpm audit --prod --json
pnpm audit --json
```

The API coverage script now includes `--no-file-parallelism` so integration tests do not race on shared test records. Coverage configuration is in each project's `vitest.config.ts`; current scripts are in the respective `package.json` files.

## 7. Remaining metrics limitations

- Lighthouse here measures a local production build with controlled emulation. It does not provide field Web Vitals or production performance.
- No analytics/telemetry was installed for active users, feature adoption, retention, production uptime, or real-traffic API latency.
- axe results are automated findings on the seven scanned routes. They are not a complete manual keyboard/screen-reader audit.
- Dependency audit results are snapshots; registry advisories and patch availability change over time.
